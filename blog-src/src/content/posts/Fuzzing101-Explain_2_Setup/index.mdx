## 1. 퍼징이란 무엇인가

**퍼징(Fuzz testing)** 은 프로그램에 무작위로 생성하거나 변형한 입력을 대량으로 밀어넣고,
크래시·행(hang)·메모리 오류 같은 비정상 동작이 발생하는지 감시하는 자동화된 소프트웨어 테스트 기법이다.

핵심 아이디어는 단순하다. **"사람이 생각하지 못한 입력을 기계가 대신 수백만 번 시도한다."**

일반적인 유닛 테스트가 "개발자가 예상한 케이스"를 검증한다면, 퍼징은 그 반대다.
예상하지 못한 입력에서 시스템이 어떻게 무너지는지를 찾는다.
실제로 OpenSSL, Chrome, Linux 커널 등에서 발견된 상당수의 메모리 손상 취약점이 퍼징으로 나왔다.

### 1-1. 이게 왜 효과가 있을까?

파일 포맷 파서, 네트워크 프로토콜 구현, 압축 라이브러리처럼
**"신뢰할 수 없는 입력을 직접 해석하는 코드"** 가 퍼징의 주 표적이다.
이런 코드는 경계 조건이 많고, 잘못된 길이 필드 하나로 버퍼 오버플로가 나기 쉽다.

C/C++처럼 메모리 안전성이 보장되지 않는 언어로 작성된 파서라면 효과가 특히 클 수 있다.

> 개인적으로 생각할 때에는 Fuzzer는 exploitable한 취약점 부분을 직접적으로 찾을 수는 없더라도, 코드가 vulnerable하다는 것 자체에 대해서는 거짓말을 하지 않는다.

### 1-2. 퍼저의 분류

#### 입력 생성 방식 기준

| 방식 | 설명 | 특징 |
|---|---|---|
| **Mutation-based** | 기존 시드(seed) 파일을 비트 뒤집기, 블록 삽입/삭제 등으로 변형 | 준비가 쉽다. 포맷 지식 불필요. AFL, honggfuzz |
| **Generation-based** | 포맷 명세나 문법(grammar)을 기반으로 입력을 처음부터 생성 | 구조가 복잡한 대상(JS 엔진, SQL)에 강함. Fuzzilli, Peach |

Mutation 방식은 시드가 나쁘면 성능이 급격히 떨어진다.
보통 seed를 넣을 때에는 정상적으로 작동하는 바이너리나 텍스트를 seed로 넣어야 crash를 찾을 확률이 높아진다.

반대로 Generation 방식은 문법을 직접 작성해야 해서 초기 비용이 크다.

#### 대상에 대한 지식 수준 기준

| 방식 | 설명 |
|---|---|
| **Black-box** | 내부를 전혀 모른 채 입력만 던진다. 가장 단순하지만 효율이 낮다 |
| **Grey-box** | 계측(instrumentation)으로 실행 경로 정보를 수집해 피드백에 활용. 현대 퍼저의 주류 |
| **White-box** | 심볼릭 실행 등으로 경로 조건을 풀어 입력을 도출. 정확하지만 느리고 확장이 어렵다 |

#### 실행 구조 기준

- **Fork server 방식** — 대상을 매번 fork해서 실행. AFL의 기본 동작.
- **Persistent mode** — 한 프로세스 안에서 입력만 바꿔가며 반복 호출. 프로세스 생성 비용이 없어 수십 배 빠르다.
- **In-process** — 대상 라이브러리 함수를 직접 호출하는 하네스(harness)를 작성. libFuzzer가 대표적.
- **Emulation 기반** — 소스가 없을 때 QEMU 등으로 에뮬레이션하며 커버리지를 수집. AFL++ QEMU mode.

### 1-3. 커버리지 기반 진화형 퍼저 (Coverage-guided evolutionary fuzzer)

AFL, libFuzzer, honggfuzz는 모두 이 범주에 속하며, 현재 실전에서 가장 성과가 좋은 방식이다.
이름 그대로 두 가지 개념이 결합돼 있다.

**Evolutionary (진화형)**
초기 시드 집합에서 출발해, 변형을 가하고 그중 "좋은" 입력만 남겨 다음 세대의 재료로 삼는다.
진화 알고리즘에서 차용한 메타휴리스틱이다.

**Coverage-guided (커버리지 기반)**
그 "좋다"의 판단 기준이 바로 **코드 커버리지**다.
계측을 통해 각 입력이 어떤 실행 경로를 밟았는지 기록하고,
**새로운 경로(엣지)를 열은 입력만** 코퍼스에 보존한다.

```
[시드 코퍼스] ──▶ [변형(mutation)] ──▶ [실행 + 커버리지 수집]
      ▲                                          │
      │                                          ▼
      └────── 새 경로를 발견한 입력만 저장 ◀── [판정]
                                                 │
                                                 ▼
                                          [크래시면 별도 저장]
```

이 피드백 루프 덕분에, 퍼저는 매직 넘버 검사나 체크섬 같은 관문을 무작위 입력에 비해서는 쉽게 통과해낸다.
한 바이트씩 맞아 들어갈 때마다 "새로운 경로"로 인정받아 그 입력이 살아남기 때문이다.

### 1-4. 계측(instrumentation)이 핵심이다

여기서 반드시 짚고 넘어가야 할 것이 **계측**이다.
커버리지 정보를 수집하려면 대상 바이너리의 모든 분기점에 기록 코드가 삽입돼 있어야 한다.

AFL++는 이를 위해 자체 컴파일러 래퍼(wrapper)를 제공한다.

| 컴파일러 | 설명 |
|---|---|
| `afl-clang-fast` | LLVM 패스 기반. 가장 무난한 기본 선택 |
| `afl-clang-lto` | LTO(Link Time Optimization) 활용. 엣지 충돌이 없어 정확도가 높다 |
| `afl-gcc-fast` | GCC 플러그인 기반 |
| QEMU mode (`-Q`) | 소스가 없는 바이너리용. 느리지만 재컴파일 불필요 |

**일반 gcc로 빌드한 바이너리를 퍼징하려 하면 실패한다.**
일반적으로 퍼징을 처음 시도할 때 가장 많이 걸리는 함정이고, 뒤의 트러블슈팅 절에서 다시 다룰 예정이다.

### 1-5. Sanitizer와 함께 쓰기

퍼징의 판정 기준이 **crash** 인데, <span style={{ color: '#FF3333' }}>메모리 오류는 **항상** 즉시 크래시로 이어지지 **않는다**.</span>

힙 버퍼를 몇 바이트 넘겨 읽어도 프로그램은 태연히 계속 돌아갈 수 있다.

**ASan(AddressSanitizer)** 같은 새니타이저를 함께 켜면 이런 조용한 오류를 즉시 abort로 바꿔주기 때문에 탐지율이 크게 올라간다.

```bash
AFL_USE_ASAN=1 CC=afl-clang-lto ./configure ...
```

대신 실행 속도가 2~3배 느려지고 메모리를 많이 쓰므로,
`afl-fuzz` 실행 시 `-m none` 으로 메모리 제한을 푸는 경우가 많다.

### 1-6. 주요 퍼저

- **[AFL++](https://github.com/AFLplusplus/AFLplusplus)** — AFL의 후속 포크. 현재 사실상의 표준. 이 코스에서 사용한다.
- **[libFuzzer](https://llvm.org/docs/LibFuzzer.html)** — LLVM 내장. in-process 방식이라 라이브러리 함수 단위 퍼징에 적합.
- **[honggfuzz](https://github.com/google/honggfuzz)** — 구글에서 만든 또 하나의 커버리지 기반 퍼저.
- **[Fuzzilli](https://github.com/googleprojectzero/fuzzilli)** — JS 엔진 전용. 문법 기반 생성 방식. Exercise 10에서 등장.

sudo apt update

### 3-2. AFL++ 설치

apt 저장소 버전은 오래된 경우가 많으니 소스에서 빌드하는 편이 낫다.

```bash
# LLVM 툴체인
sudo apt install -y lld llvm llvm-dev clang

# GCC 플러그인 개발 헤더 (버전은 시스템 gcc에 맞춰서)
GCCVER=$(gcc -dumpversion | cut -d. -f1)
sudo apt install -y gcc-${GCCVER}-plugin-dev libstdc++-${GCCVER}-dev

# AFL을 설치할 폴더로 이동 후
git clone https://github.com/AFLplusplus/AFLplusplus
cd AFLplusplus
make distrib
sudo make install
```

설치 확인:

```bash
afl-fuzz --help | head -3
which afl-clang-fast afl-clang-fast++ afl-clang-lto
```

`afl-fuzz++4.xx` 배너가 뜨고 컴파일러 경로들이 나오면 성공이다.

### error solve

#### AFL++ 빌드 시 자주 나는 에러

`make distrib`은 QEMU/Unicorn/FRIDA 모드까지 전부 빌드하려 하기 때문에 의존성이 하나라도 빠지면 중간에 멈춘다. 먼저 빌드 대상을 줄여서 원인을 좁히는 게 빠르다. (경험상 그렇다)

```bash
cd AFLplusplus
make source-only     # QEMU/Unicorn 제외, 코어 + LLVM 모드만
# 또는
make                 # 가장 기본
```

#### 에러별 대응

**`llvm-config not found` / `LLVM_CONFIG` 관련**

여러 버전이 깔려 있으면 명시해줘야 한다.

```bash
ls /usr/bin/llvm-config*                    # 설치된 버전 확인
sudo apt install -y llvm-18 llvm-18-dev clang-18
make LLVM_CONFIG=llvm-config-18
```

**`afl-clang-lto` 가 안 만들어짐 / `ld.lld not found`**

LTO 모드는 `lld`가 필수다.

```bash
sudo apt install -y lld-18
which ld.lld ld.lld-18
```

없으면 빌드 로그에 `[-] LLVM_LTO: not building` 정도만 뜨고 조용히 넘어가므로, 나중에 `afl-clang-lto`를 쓰는 Exercise 2·3·4에서 "command not found"로 터지게 된다.

**`cannot find gcc plugin headers` / `plugin/include/gcc-plugin.h`**

```bash
GCCVER=$(gcc -dumpversion | cut -d. -f1)
sudo apt install -y gcc-${GCCVER}-plugin-dev libstdc++-${GCCVER}-dev
```

**`Python.h: No such file or directory`**

```bash
sudo apt install -y python3-dev python3-setuptools
```

**`cargo: command not found`**

일부 커스텀 뮤테이터가 Rust를 요구한다. 안 쓸 거면 `make source-only`로 우회하거나:

```bash
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh -s -- -y
. "$HOME/.cargo/env"
# or
source "$HOME/.cargo/env"
```

**QEMU 모드 빌드 실패 (`glib-2.0 not found`, `pixman` 등)**

Exercise 8 전까지는 필요 없다. 나중에 필요할 때 따로 빌드하면 된다.

```bash
sudo apt install -y libglib2.0-dev libpixman-1-dev ninja-build
cd AFLplusplus/qemu_mode && ./build_qemu_support.sh
```

**한 방에 의존성 몰아넣기**

```bash
sudo apt update
sudo apt install -y build-essential git wget curl \
    python3-dev python3-setuptools automake cmake ninja-build \
    flex bison libglib2.0-dev libpixman-1-dev \
    llvm llvm-dev clang lld cargo \
    gcc-$(gcc -dumpversion | cut -d. -f1)-plugin-dev \
    libstdc++-$(gcc -dumpversion | cut -d. -f1)-dev
```

**빌드 결과 검증** — 에러 없이 끝나도 어떤 모드가 빠졌는지는 따로 확인해야 한다.

```bash
cd AFLplusplus
ls -1 afl-clang-fast afl-clang-lto afl-gcc-fast afl-fuzz 2>&1
```

없는 게 있으면 위 항목 중 해당 의존성이 빠진 것이다. 의존성 설치 후에는 `make clean && make` 로 다시 빌드하면 된다.

#### PATH 등록

`sudo make install`을 했다면 `/usr/local/bin`에 들어가므로 별도 설정이 필요 없다. 설치 없이 소스 디렉터리에서 쓰려는 경우에만 아래가 필요하다.

**현재 셸에만 임시 적용**

```bash
export PATH="$PWD/AFLplusplus:$PATH" # git clone을 한 dir에서
export AFL_PATH="$PWD/AFLplusplus"  # git clone을 한 dir에서
```

`AFL_PATH`는 `afl-gcc`/`afl-clang`이 `afl-as`, `afl-llvm-rt.o` 같은 보조 파일을 찾는 데 쓴다. PATH만 잡고 이걸 빼먹으면 컴파일 단계에서 `Oops, unable to find the 'afl-as' binary` 가 난다.

**셸 설정 파일에 영구 등록**

```bash
# bash
# git clone을 한 dir에서
cat >> ~/.bashrc << 'EOF'

# AFL++
export AFL_PATH="$PWD/AFLplusplus"
export PATH="$AFL_PATH:$PATH"
EOF

source ~/.bashrc
```

zsh를 쓴다면 `~/.zshrc`로 바꾸면 됩니다. 어느 셸인지 모르겠으면:

```bash
echo $SHELL
```

**셸 자동 판별해서 넣기**

```bash
# git clone을 한 dir에서

RC=~/.bashrc
[ -n "$ZSH_VERSION" ] && RC=~/.zshrc
cat >> "$RC" << 'EOF'

# AFL++
export AFL_PATH="$PWD/AFLplusplus"
export PATH="$AFL_PATH:$PATH"
EOF
source "$RC"
```

**확인**

```bash
which afl-fuzz afl-clang-fast
echo $PATH | tr ':' '\n' | head
afl-fuzz --help | head -3
```


### 3-3. `core_pattern` 설정

리눅스는 기본적으로 코어 덤프를 `apport` 같은 외부 유틸리티로 넘긴다.
이 상태에서는 크래시 통지가 지연돼 퍼저가 크래시를 타임아웃으로 오인한다.

이 때는 AFL++는 아예 실행을 거부한다.

```bash
cat /proc/sys/kernel/core_pattern            # 현재 값
echo core | sudo tee /proc/sys/kernel/core_pattern
```

> **주의**: `sudo su` 로 전환한 뒤 `echo core > /proc/sys/kernel/core_pattern` 을 쓰면
> 리다이렉션이 원래 셸 권한으로 평가돼 `Permission denied` 가 난다.
> 반드시 `sudo tee` 를 쓸 것.

**재부팅하면 초기화된다.** 매번 하기 귀찮다면 영구 설정:

```bash
echo 'kernel.core_pattern=core' | sudo tee /etc/sysctl.d/99-afl.conf
sudo sysctl --system
```

## 5. `plygnd` 디렉터리 구조 설계

### 5-1. 왜 필요한가

원본 Readme들은 이런 식으로 시작한다.

```bash
cd $HOME
mkdir fuzzing_xpdf && cd fuzzing_xpdf/
wget https://dl.xpdfreader.com/old/xpdf-3.02.tar.gz
```

전용 VM을 쓴다면 홈 디렉터리가 어질러져도 상관없다.
하지만 평소 쓰는 서버나 개인 계정에서 실습한다면 이야기가 다르다.

- 소스 트리, 빌드 산출물, 크래시 파일이 홈에 그대로 쌓인다
- Exercise가 10개니 `fuzzing_xpdf`, `fuzzing_libexif`, `fuzzing_tiff` ... 가 전부 홈에 널린다
- 어느 실습 결과물인지 나중에 구분이 안 된다

그래서 **각 Exercise 폴더 안에 `plygnd`(playground) 디렉터리를 만들고,
그 안에서만 작업하도록** 구조를 바꾼다.

```
~/study/Fuzzing101/
├── Exercise_1/
│   ├── Readme.md
│   ├── Images/
│   └── plygnd/          ← 여기가 $STATIC_PATH
│       └── fuzzing_xpdf/
│           ├── xpdf-3.02/
│           ├── install/
│           ├── pdf_examples/
│           └── out/
├── Exercise_2/
│   ├── Readme.md
│   └── plygnd/          ← Exercise 2의 $STATIC_PATH
└── ...
```

실습 자료(Readme, 이미지)와 실습 결과물이 같은 폴더에 묶이니
나중에 다시 볼 때 맥락이 붙어 있어 좋다.

### 5-2. 디렉터리 생성

```bash
cd ~/study/Fuzzing101
for i in $(seq 1 10); do
    mkdir -p "Exercise_$i/plygnd"
done
```

### 5-3. git에서 제외

`plygnd` 안에는 수 GB의 소스와 빌드 산출물이 쌓인다.
클론한 저장소는 git 저장소이므로 `.gitignore`에 넣어 `git status`를 깨끗하게 유지하자.

```bash

```

## 6. `$HOME` → `$STATIC_PATH` 치환

이제 Readme들의 `$HOME`을 `$STATIC_PATH`로 바꾼다.

### 6-1. 왜 `$PWD`가 아니라 별도 변수인가

처음엔 `$PWD`로 바꿔볼까 싶었지만, cd 를 할 때마다 값이 바뀌어서 사용을 하면 안된다. `$HOME` 을 `$STATIC_PATH`로 바꾸자.

Readme는 이런 흐름으로 진행된다.

```bash
cd plygnd
STATIC_PATH=$PWD
cd $STATIC_PATH/fuzzing_xpdf/xpdf-3.02/     # 여기서 디렉터리 이동
./configure --prefix="$STATIC_PATH/fuzzing_xpdf/install/"   # 이 시점의 기준 경로는?
```

`$PWD`였다면 두 번째 줄의 기준이 이미 `xpdf-3.02/`로 바뀌어 있어
`install` 디렉터리가 엉뚱한 곳에 생긴다.
**한 번 정하면 세션 내내 고정되는 변수**가 필요하다. 그래서 `$STATIC_PATH`다.


## 7. `$STATIC_PATH`를 `.bashrc`에 넣지 않는 이유

한 번 export 해두면 편할 것 같아서 `~/.bashrc`에 넣고 싶은 유혹이 있다.
**하지만 넣으면 안 된다.**

`STATIC_PATH`는 Exercise마다 값이 다르다.
`.bashrc`에 Exercise 1 경로를 박아두고 Exercise 3을 진행하면 어떻게 될까.

```bash
# .bashrc: export STATIC_PATH=~/study/Fuzzing101/Exercise_1/plygnd

cd ~/study/Fuzzing101/Exercise_3/plygnd
# Readme를 따라 붙여넣기...
./configure --prefix="$STATIC_PATH/fuzzing_tcpdump/install/"
# → Exercise_1/plygnd 아래에 tcpdump가 설치된다
```

에러도 안 나고 조용히 잘못된 곳에 설치된다. 이런 종류가 제일 잡기 어렵다.

**원칙: 작업할 `plygnd`에 들어가서, 그 자리에서 `$PWD`로 지정한다.**

```bash
cd ~/study/Fuzzing101/Exercise_3/plygnd
export STATIC_PATH=$PWD
echo $STATIC_PATH      # 매번 눈으로 확인하는게 좋다....
```

`$PWD`를 값으로 쓰되, `STATIC_PATH`에 **한 번 복사해서 고정**하는 것이다.
이후 `cd`로 어디를 돌아다녀도 `STATIC_PATH`는 그대로다.
`$PWD`의 편리함과 고정 변수의 안정성을 둘 다 취한다.

`export`를 붙이는 이유는 `configure`, `make`, `afl-fuzz` 같은
**자식 프로세스에도 전달되어야** 하기 때문이다.
`export` 없이 `STATIC_PATH=$PWD`만 하면 현재 셸에서의 문자열 확장은 되지만
자식 프로세스 환경에는 들어가지 않는다.

그리고 사실...tmux써서 퍼징을 백그라운드로도 돌릴 수 있게 할 것이기 때문에 .bashrc에는 안넣는게 좋다.

## 8. tmux로 세션 유지하기

### 8-1. 왜 필요한가

SSH로 원격 서버에 붙어 실습한다면 tmux는 선택이 아니라 필수다.

- 빌드가 수 분~수십 분 걸린다
- **퍼징은 크래시 하나 찾는 데 1~2시간이 걸린다**
- SSH 연결이 끊기면 그 셸의 프로세스도 함께 죽는다

노트북 덮개를 닫거나, 와이파이가 잠깐 끊기거나, 회사에서 집으로 이동하는 순간
2시간 돌린 퍼징이 통째로 날아간다.

tmux 세션 안에서 돌리면 프로세스가 서버 쪽에 남아 있어,
재접속 후 `attach` 하면 **돌아가던 화면 그대로** 이어서 볼 수 있다.

### 8-2. 워크플로우

**접속 → plygnd로 이동 → tmux 세션 생성 → 그 안에서 환경 설정** 순서다.

```bash
# 1) 서버 접속
ssh user@myserver

# 2) 작업할 exercise의 plygnd로 이동
cd ~/study/Fuzzing101/Exercise_1/plygnd

# 3) 그 자리에서 tmux 세션 생성
#    (tmux는 현재 디렉터리를 물려받으므로 세션 안에서도 plygnd에 있다)
tmux new -s ex1

# ── 여기서부터는 tmux 세션 안 ──

# 4) 환경 설정
export STATIC_PATH=$PWD
echo $STATIC_PATH        # .../Exercise_1/plygnd 확인

# 5) 이제 Readme를 따라 진행
```

세션 이름을 `ex1`, `ex3` 처럼 Exercise 번호로 지으면
여러 실습을 병행할 때 헷갈리지 않는다.

> **중요**: `STATIC_PATH`는 **tmux 세션 안의 셸**에서 export 해야 한다.
> 바깥 셸에서 설정하고 나중에 attach 해봐야, 이미 떠 있는 tmux 셸에는 반영되지 않는다.
> 환경변수는 프로세스 생성 시점에 상속되기 때문이다.

### 8-3. 분리와 재접속

```
Ctrl+b 를 누르고 뗀 뒤 → d      # 분리(detach). SSH를 끊어도 계속 돈다
```

나중에 다시:

```bash
ssh user@myserver
tmux ls                  # 살아있는 세션 목록
tmux attach -t ex1       # 다시 붙기
```

`tmux ls` 출력 예시:

```
ex1: 1 windows (created Sun Jul 26 15:20:11 2026)
```

### 8-4. 자주 쓰는 키

모두 **prefix(`Ctrl+b`)를 먼저 누르고 뗀 뒤** 해당 키를 누른다.

| 키 | 동작 |
|---|---|
| `d` | detach |
| `[` | 스크롤 모드 진입 (`q`로 나감) |
| `c` | 새 창 생성 |
| `n` / `p` | 다음 / 이전 창 |
| `"` | 가로 분할 |
| `%` | 세로 분할 |
| `방향키` | 분할된 pane 간 이동 |
| `&` | 현재 창 종료 |

AFL의 상태 화면은 터미널을 계속 다시 그리기 때문에 마우스 휠 스크롤이 안 먹는다.
지나간 로그를 보려면 `Ctrl+b` → `[` 로 스크롤 모드에 들어가야 한다.

### 8-5. 화면 분할해서 모니터링

퍼징 화면은 그대로 두고 다른 pane에서 진행 상황을 확인할 수 있다.

```bash
# Ctrl+b " 로 가로 분할한 뒤, 아래쪽 pane에서
export STATIC_PATH=~/study/Fuzzing101/Exercise_1/plygnd   # 새 pane은 별도 셸

watch -n 5 afl-whatsup $STATIC_PATH/fuzzing_xpdf/out/

# 또는 크래시 개수만
watch -n 10 'ls $STATIC_PATH/fuzzing_xpdf/out/default/crashes/ 2>/dev/null | wc -l'
```

**새로 만든 pane은 별도의 셸**이므로 `STATIC_PATH`를 다시 export 해야 한다.

### 8-6. 편의 설정 (선택)

`~/.tmux.conf`:

```
set -g mouse on              # 마우스 스크롤 / pane 선택
set -g history-limit 50000   # 스크롤백 버퍼 확대
set -g status-bg colour235
```

적용:

```bash
tmux source-file ~/.tmux.conf
```

### 8-7. 세션 정리

```bash
tmux kill-session -t ex1     # 특정 세션
tmux kill-server             # 전체
```

퍼징을 멈출 때는 attach 한 뒤 `Ctrl+c`로 afl-fuzz를 먼저 정상 종료시키자.
`out/` 디렉터리의 상태 파일이 깔끔하게 저장된다.

## 10. 정리

이 글에서 한 일을 요약하면 이렇다.

1. **퍼징 개념 정리** — 커버리지 기반 진화형 퍼저가 왜 효과적인지, 계측이 왜 필수인지
2. **저장소 정리** — 클론 후 폴더명의 공백을 언더바로 치환
3. **구조 재설계** — 각 Exercise 안에 `plygnd`를 만들어 실습 결과물을 격리
4. **경로 변수 교체** — Readme의 `$HOME`을 `$STATIC_PATH`로 일괄 치환
5. **운용 원칙** — `.bashrc`에 박지 않고, plygnd에서 tmux를 열어 그 안에서 export

원본 코스는 "전용 VM을 쓴다"는 전제 위에 있다.
그 전제를 걷어내고 일반 서버에서 쓰려면 **경로 격리**와 **세션 유지**,
이 두 가지만 해결하면 된다. 나머지는 원본 Readme를 그대로 따라가면 된다.

이제 Exercise 1의 CVE-2019-13288을 찾으러 가보자.
