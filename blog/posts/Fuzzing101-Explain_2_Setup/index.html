퍼징 입문 — 개념부터 Fuzzing101 로컬 환경 세팅까지

이번 글은 퍼징(Fuzzing)이 무엇인지 정리하고, Fuzzing101을 VM 이미지 없이 내 서버(ubuntu)에서 편하게 진행하기 위한 환경 세팅 과정을 다룬다.

기존 환경은 VM사용을 전제로 Redme를 작성했기에 모든 경로를 $HOME 기준으로 안내했다. 이번 블로그는 각 Exercise 폴더 안에 plygnd(playground) 디렉터리를 만들고 그곳을 $STATIC_PATH로 잡아서, 실습 결과물이 홈 디렉터리를 어지럽히지 않도록 구성했다.

1. 퍼징이란 무엇인가

퍼징(Fuzz testing) 은 프로그램에 무작위로 생성하거나 변형한 입력을 대량으로 밀어넣고, 크래시·행(hang)·메모리 오류 같은 비정상 동작이 발생하는지 감시하는 자동화된 소프트웨어 테스트 기법이다.

핵심 아이디어는 단순하다. “사람이 생각하지 못한 입력을 기계가 대신 수백만 번 시도한다.”

일반적인 유닛 테스트가 “개발자가 예상한 케이스”를 검증한다면, 퍼징은 그 반대다. 예상하지 못한 입력에서 시스템이 어떻게 무너지는지를 찾는다. 실제로 OpenSSL, Chrome, Linux 커널 등에서 발견된 상당수의 메모리 손상 취약점이 퍼징으로 나왔다.

1-1. 이게 왜 효과가 있을까?

파일 포맷 파서, 네트워크 프로토콜 구현, 압축 라이브러리처럼 “신뢰할 수 없는 입력을 직접 해석하는 코드” 가 퍼징의 주 표적이다. 이런 코드는 경계 조건이 많고, 잘못된 길이 필드 하나로 버퍼 오버플로가 나기 쉽다.

C/C++처럼 메모리 안전성이 보장되지 않는 언어로 작성된 파서라면 효과가 특히 클 수 있다.

개인적으로 생각할 때에는 Fuzzer는 exploitable한 취약점 부분을 직접적으로 찾을 수는 없더라도, 코드가 vulnerable하다는 것 자체에 대해서는 거짓말을 하지 않는다.

1-2. 퍼저의 분류

입력 생성 방식 기준

방식설명특징
Mutation-based기존 시드(seed) 파일을 비트 뒤집기, 블록 삽입/삭제 등으로 변형준비가 쉽다. 포맷 지식 불필요. AFL, honggfuzz
Generation-based포맷 명세나 문법(grammar)을 기반으로 입력을 처음부터 생성구조가 복잡한 대상(JS 엔진, SQL)에 강함. Fuzzilli, Peach

Mutation 방식은 시드가 나쁘면 성능이 급격히 떨어진다. 보통 seed를 넣을 때에는 정상적으로 작동하는 바이너리나 텍스트를 seed로 넣어야 crash를 찾을 확률이 높아진다.

반대로 Generation 방식은 문법을 직접 작성해야 해서 초기 비용이 크다.

대상에 대한 지식 수준 기준

방식설명
Black-box내부를 전혀 모른 채 입력만 던진다. 가장 단순하지만 효율이 낮다
Grey-box계측(instrumentation)으로 실행 경로 정보를 수집해 피드백에 활용. 현대 퍼저의 주류
White-box심볼릭 실행 등으로 경로 조건을 풀어 입력을 도출. 정확하지만 느리고 확장이 어렵다

실행 구조 기준

  • Fork server 방식 — 대상을 매번 fork해서 실행. AFL의 기본 동작.
  • Persistent mode — 한 프로세스 안에서 입력만 바꿔가며 반복 호출. 프로세스 생성 비용이 없어 수십 배 빠르다.
  • In-process — 대상 라이브러리 함수를 직접 호출하는 하네스(harness)를 작성. libFuzzer가 대표적.
  • Emulation 기반 — 소스가 없을 때 QEMU 등으로 에뮬레이션하며 커버리지를 수집. AFL++ QEMU mode.

1-3. 커버리지 기반 진화형 퍼저 (Coverage-guided evolutionary fuzzer)

AFL, libFuzzer, honggfuzz는 모두 이 범주에 속하며, 현재 실전에서 가장 성과가 좋은 방식이다. 이름 그대로 두 가지 개념이 결합돼 있다.

Evolutionary (진화형) 초기 시드 집합에서 출발해, 변형을 가하고 그중 “좋은” 입력만 남겨 다음 세대의 재료로 삼는다. 진화 알고리즘에서 차용한 메타휴리스틱이다.

Coverage-guided (커버리지 기반) 그 “좋다”의 판단 기준이 바로 코드 커버리지다. 계측을 통해 각 입력이 어떤 실행 경로를 밟았는지 기록하고, 새로운 경로(엣지)를 열은 입력만 코퍼스에 보존한다.

이 피드백 루프 덕분에, 퍼저는 매직 넘버 검사나 체크섬 같은 관문을 무작위 입력에 비해서는 쉽게 통과해낸다. 한 바이트씩 맞아 들어갈 때마다 “새로운 경로”로 인정받아 그 입력이 살아남기 때문이다.

1-4. 계측(instrumentation)이 핵심이다

여기서 반드시 짚고 넘어가야 할 것이 계측이다. 커버리지 정보를 수집하려면 대상 바이너리의 모든 분기점에 기록 코드가 삽입돼 있어야 한다.

AFL++는 이를 위해 자체 컴파일러 래퍼(wrapper)를 제공한다.

컴파일러설명
afl-clang-fastLLVM 패스 기반. 가장 무난한 기본 선택
afl-clang-ltoLTO(Link Time Optimization) 활용. 엣지 충돌이 없어 정확도가 높다
afl-gcc-fastGCC 플러그인 기반
QEMU mode (-Q)소스가 없는 바이너리용. 느리지만 재컴파일 불필요

일반 gcc로 빌드한 바이너리를 퍼징하려 하면 실패한다. 일반적으로 퍼징을 처음 시도할 때 가장 많이 걸리는 함정이고, 뒤의 트러블슈팅 절에서 다시 다룰 예정이다.

1-5. Sanitizer와 함께 쓰기

퍼징의 판정 기준이 crash 인데, 메모리 오류는 항상 즉시 크래시로 이어지지 않는다.

힙 버퍼를 몇 바이트 넘겨 읽어도 프로그램은 태연히 계속 돌아갈 수 있다.

ASan(AddressSanitizer) 같은 새니타이저를 함께 켜면 이런 조용한 오류를 즉시 abort로 바꿔주기 때문에 탐지율이 크게 올라간다.

대신 실행 속도가 2~3배 느려지고 메모리를 많이 쓰므로, afl-fuzz 실행 시 -m none 으로 메모리 제한을 푸는 경우가 많다.

1-6. 주요 퍼저

  • AFL++ — AFL의 후속 포크. 현재 사실상의 표준. 이 코스에서 사용한다.
  • libFuzzer — LLVM 내장. in-process 방식이라 라이브러리 함수 단위 퍼징에 적합.
  • honggfuzz — 구글에서 만든 또 하나의 커버리지 기반 퍼저.
  • Fuzzilli — JS 엔진 전용. 문법 기반 생성 방식. Exercise 10에서 등장.

5. plygnd 디렉터리 구조 설계

5-1. 왜 필요한가

원본 Readme들은 이런 식으로 시작한다.

전용 VM을 쓴다면 홈 디렉터리가 어질러져도 상관없다. 하지만 평소 쓰는 서버나 개인 계정에서 실습한다면 이야기가 다르다.

  • 소스 트리, 빌드 산출물, 크래시 파일이 홈에 그대로 쌓인다
  • Exercise가 10개니 fuzzing_xpdf, fuzzing_libexif, fuzzing_tiff … 가 전부 홈에 널린다
  • 어느 실습 결과물인지 나중에 구분이 안 된다

그래서 각 Exercise 폴더 안에 plygnd(playground) 디렉터리를 만들고, 그 안에서만 작업하도록 구조를 바꾼다.

실습 자료(Readme, 이미지)와 실습 결과물이 같은 폴더에 묶이니 나중에 다시 볼 때 맥락이 붙어 있어 좋다.

5-2. 디렉터리 생성

5-3. git에서 제외

plygnd 안에는 수 GB의 소스와 빌드 산출물이 쌓인다. 클론한 저장소는 git 저장소이므로 .gitignore에 넣어 git status를 깨끗하게 유지하자.

6. $HOME → $STATIC_PATH 치환

이제 Readme들의 $HOME을 $STATIC_PATH로 바꾼다.

6-1. 왜 $PWD가 아니라 별도 변수인가

처음엔 $PWD로 바꿔볼까 싶었지만, cd 를 할 때마다 값이 바뀌어서 사용을 하면 안된다. $HOME 을 $STATIC_PATH로 바꾸자.

Readme는 이런 흐름으로 진행된다.

$PWD였다면 두 번째 줄의 기준이 이미 xpdf-3.02/로 바뀌어 있어 install 디렉터리가 엉뚱한 곳에 생긴다. 한 번 정하면 세션 내내 고정되는 변수가 필요하다. 그래서 $STATIC_PATH다.

7. $STATIC_PATH를 .bashrc에 넣지 않는 이유

한 번 export 해두면 편할 것 같아서 ~/.bashrc에 넣고 싶은 유혹이 있다. 하지만 넣으면 안 된다.

STATIC_PATH는 Exercise마다 값이 다르다. .bashrc에 Exercise 1 경로를 박아두고 Exercise 3을 진행하면 어떻게 될까.

에러도 안 나고 조용히 잘못된 곳에 설치된다. 이런 종류가 제일 잡기 어렵다.

원칙: 작업할 plygnd에 들어가서, 그 자리에서 $PWD로 지정한다.

$PWD를 값으로 쓰되, STATIC_PATH에 한 번 복사해서 고정하는 것이다. 이후 cd로 어디를 돌아다녀도 STATIC_PATH는 그대로다. $PWD의 편리함과 고정 변수의 안정성을 둘 다 취한다.

export를 붙이는 이유는 configure, make, afl-fuzz 같은 자식 프로세스에도 전달되어야 하기 때문이다. export 없이 STATIC_PATH=$PWD만 하면 현재 셸에서의 문자열 확장은 되지만 자식 프로세스 환경에는 들어가지 않는다.

그리고 사실…tmux써서 퍼징을 백그라운드로도 돌릴 수 있게 할 것이기 때문에 .bashrc에는 안넣는게 좋다.

8. tmux로 세션 유지하기

8-1. 왜 필요한가

SSH로 원격 서버에 붙어 실습한다면 tmux는 선택이 아니라 필수다.

  • 빌드가 수 분~수십 분 걸린다
  • 퍼징은 크래시 하나 찾는 데 1~2시간이 걸린다
  • SSH 연결이 끊기면 그 셸의 프로세스도 함께 죽는다

노트북 덮개를 닫거나, 와이파이가 잠깐 끊기거나, 회사에서 집으로 이동하는 순간 2시간 돌린 퍼징이 통째로 날아간다.

tmux 세션 안에서 돌리면 프로세스가 서버 쪽에 남아 있어, 재접속 후 attach 하면 돌아가던 화면 그대로 이어서 볼 수 있다.

8-2. 워크플로우

접속 → plygnd로 이동 → tmux 세션 생성 → 그 안에서 환경 설정 순서다.

세션 이름을 ex1, ex3 처럼 Exercise 번호로 지으면 여러 실습을 병행할 때 헷갈리지 않는다.

중요: STATIC_PATH는 tmux 세션 안의 셸에서 export 해야 한다. 바깥 셸에서 설정하고 나중에 attach 해봐야, 이미 떠 있는 tmux 셸에는 반영되지 않는다. 환경변수는 프로세스 생성 시점에 상속되기 때문이다.

9. 실습 시작 전 체크리스트

  • cd .../Exercise_N/plygnd — 작업할 exercise의 playground로
  • tmux new -s exN — 세션 먼저 열고
  • export STATIC_PATH=$PWD — tmux 세션 안의 셸에서
  • echo $STATIC_PATH — 경로 눈으로 확인
  • cat /proc/sys/kernel/core_pattern → core (재부팅했다면 다시)
  • nm <타깃> | grep -i afl → 계측 심볼 존재
  • 이전 out/ 디렉터리 정리
  • 환경변수는 명령 앞에 배치
